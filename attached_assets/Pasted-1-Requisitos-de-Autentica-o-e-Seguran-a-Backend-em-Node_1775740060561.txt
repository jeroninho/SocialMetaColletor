1. Requisitos de Autenticação e Segurança
Backend em Node.js + TypeScript com Express que implemente:


Validação de token OAuth2


Implementar fluxo para validar se um token OAuth2 é elegível/ativo.


Considerar o fluxo padrão: Authorization Code → Access Token → Refresh Token.


Crie serviços para lidar com tokens de APIs sociais (YouTube, Facebook, Instagram), mesmo que sejam mocks.


Criptografia de tokens


Todos os tokens OAuth2 devem ser armazenados somente no banco de dados após criptografia simétrica AES‑256‑GCM.


Criar um módulo utilitário para:


encryptToken(plaintext: string): string


decryptToken(ciphertext: string): string


Usar uma SECRET_KEY vinda de variável de ambiente (process.env.TOKEN_SECRET).


Nunca logar tokens em texto puro.


Sistema de LOGIN / Usuários


Model de usuário com campos:


id (uuid v4)


email (único)


nome


senhaHash (senha criptografada)


timestamps (createdAt, updatedAt)


Rotas:


POST /api/auth/register


Recebe: email, nome, senha


Valida dados


Criptografa senha com BCRYPT (salt adequado, ex: 10+ rounds)


Salva usuário com uuid


POST /api/auth/login


Recebe: email, senha


Valida credenciais


Gera um JSON Web Token (JWT) de acesso para o usuário logado


Configurar expiração razoável (ex: 15min–1h) e, opcionalmente, refresh token


Uso de JSONWEBTOKEN (JWT)


Criar middleware authMiddleware que:


Lê o JWT do header Authorization: Bearer <token>


Valida assinatura e expiração


Anexa o usuário autenticado ao req.user


Proteger rotas sensíveis como /api/dashboard/* e /api/metadata/*.


Criptografia de senhas com BCRYPT


Usar bcrypt para:


Hash da senha no registro


Comparação na autenticação (bcrypt.compare)


Nunca armazenar senha em texto puro.


2. Arquitetura de Integrações com Redes Sociais
Quero uma arquitetura de backend bem estruturada, com:


Services/Providers isolados


Criar classes ou módulos:


YouTubeProvider.ts


MetaProvider.ts (para Facebook e Instagram)


Cada provider deve:


Isolar lógica de autenticação com a API externa


Ter métodos como:


getChannelStats(userId)


getRecentEngagement(userId)


etc. (pode ser mockado, mas bem estruturado)


As rotas do Express não devem conter lógica de integração direta — apenas chamar services.


Job Queue (Redis + BullMQ)


Integrar Redis + BullMQ para filas de jobs.


Criar fila para sincronização de metadados:


Ex: metadataSyncQueue


Rota:


POST /api/metadata/sync


Em vez de fazer tudo síncrono, enfileira um job (userId, platforms, etc.)


Retorna um ID de job ou status.


Worker:


Processa jobs de sincronização, chama os providers (YouTubeProvider, MetaProvider), atualiza banco.


Suporta retentativas e tratamento de rate limiting.


Webhooks (Facebook / Instagram)


Estrutura de rotas para webhooks:


POST /api/webhooks/meta


Trate verificação de webhook (challenge) e callbacks de eventos (ex: novos posts, comentários, etc.).


Mesmo que seja um mock, quero a estrutura pronta para plugar com Meta Webhooks.


Caching com Redis


Usar Redis para cachear respostas agregadas de dashboard.


Exemplo:


Rota GET /api/dashboard/summary


Tenta retornar de cache (chave: dashboard:summary:userId)


Se não houver cache ou estiver expirado, consulta DB/serviços, monta resumo, guarda no Redis com TTL configurável (ex: 60s) e retorna.


3. Segurança – Foco em SQL Injection e Boas Práticas
Considere que o projeto usa Postgres (pode ser outro, mas mantenha a ideia):


Consultas Parametrizadas


Todas as consultas devem usar placeholders ($1, $2, etc. ou ? dependendo do driver).


Nada de string concatenada com input direto de usuário.


Uso de ORM/Query Builder


Utilize Sequelize ou Knex (ou Prisma, se preferir, mas siga a ideia).


Isso garante parametrização nativa e reduz risco de SQL Injection.


Validação de Dados


Usar joi ou zod para validar payloads:


Tipo, formato, tamanho, e-mail válido, etc.


Criar middlewares de validação para as rotas de register, login, sync metadata, etc.


Princípio do Menor Privilégio


Configurar usuário do banco no código com permissões mínimas (sem acesso root).


Deixar isso documentado no README.


Desativar múltiplas consultas


Não permitir "multi statement" em uma mesma query no driver/config do banco.


Boas práticas adicionais


Nunca versionar secrets.


Usar .env e, de preferência, dotenv-safe para garantir variáveis obrigatórias.


Explicar no README quais envs são necessários:


DATABASE_URL


REDIS_URL


JWT_SECRET


TOKEN_SECRET (para AES‑256‑GCM)


Credenciais de APIs (mockadas ou não).
